# Project 1: FastAPI LLM Service on Cloud Run (operated via MCP)

## 1. Goal

Deploy a small FastAPI service that calls the Gemini API, on GCP free tier, using
Google's MCP servers (gcloud MCP, Cloud Run MCP) to do the cloud operations through an
agent. The point is to learn GCP fundamentals while building: projects, APIs, containers,
Artifact Registry, Cloud Build, Cloud Run, Secret Manager, service accounts, IAM, logging.

**Not in scope:** building an MCP server (we are *using* MCP), RAG, databases, Pub/Sub.
Those come in later projects.

## 2. Learning objectives

| Area | What you should be able to explain after |
|---|---|
| Resource model | Project, billing account, region, enabled APIs |
| Containers | Dockerfile, image layers, Artifact Registry, tags |
| Cloud Run | Revisions, traffic, concurrency, min/max instances, scale-to-zero, cold starts |
| Secrets | Why keys live in Secret Manager, how they reach the container |
| IAM | Service account vs user account, roles, `run.invoker`, least privilege |
| Observability | Reading Cloud Logging, structured logs, request latency |
| MCP | What gcloud MCP and Cloud Run MCP expose, and where you stay in control |

## 3. System architecture

```
                         +-----------------------------+
   You (Claude Code /    |  MCP servers (control plane)|
   Claude Desktop /  --> |  - gcloud MCP (local, stdio)|
   Gemini CLI            |  - Cloud Run MCP            |
                         +--------------+--------------+
                                        | gcloud / Cloud Run API
                                        v
 +------------------------------ GCP Project (dedicated) --------------------------+
 |                                                                                  |
 |  Cloud Build ---> Artifact Registry (image) ---> Cloud Run service              |
 |                                                   |  runs as: llm-api-sa         |
 |                                                   |  env: GEMINI_API_KEY         |
 |   Secret Manager (gemini-api-key) ---- mounted ---+                              |
 |                                                   |                              |
 |   Cloud Logging <-- structured logs --------------+                              |
 |   Billing budget + alert (guardrail)              |                              |
 +---------------------------------------------------|------------------------------+
                                                     | HTTPS (outbound)
                                                     v
                                          Gemini API (AI Studio free tier)

 Client (curl / browser) --HTTPS + identity token--> Cloud Run (private service)
```

**Two planes, keep them separate in your head:**
- **Control plane:** the agent + MCP servers create and change infrastructure.
- **Data plane:** clients call your API; the API calls Gemini.

## 5. API design

| Method | Path | Purpose |
|---|---|---|
| GET | `/healthz` | Liveness; returns `{"status":"ok"}` |
| POST | `/v1/chat` | Body: `{"prompt": str, "max_output_tokens": int?}` |

`/v1/chat` response: `{"text": str, "model": str, "usage": {"input_tokens": int, "output_tokens": int}, "latency_ms": int}`

Rules:
- Validate prompt length (e.g. max 4,000 chars) to cap cost.
- Cap `max_output_tokens` server-side.
- Timeout on the Gemini call; map upstream errors to 502/504, never leak the key or raw stack traces.
- Log one structured line per request: path, status, latency, token counts. Never log prompts by default.

## 6. Configuration

| Variable | Source in prod | Notes |
|---|---|---|
| `GEMINI_API_KEY` | Secret Manager (mounted as env var) | Never in image, repo or `.env` committed |
| `GEMINI_MODEL` | Plain env var | Pick a current Flash-class model that the free tier supports; check AI Studio docs |
| `LOG_LEVEL` | Plain env var | Default `INFO` |
| `PORT` | Set by Cloud Run | App must listen on `$PORT` |

## 7. Build phases

### Phase A: Local app (no cloud)
1. Create the repo; run `uv sync` (creates the virtualenv and `uv.lock`).
2. Implement `config.py`, `schemas.py`, `services/llm.py`, `api/health.py`, `api/chat.py`, `main.py`.
3. Run with `uvicorn app.main:app --reload`; call `/v1/chat` with `curl`.
4. Write tests with the Gemini client mocked; run `pytest` and `ruff`.

**Done when:** tests pass and a real prompt returns text locally.

### Phase B: Containerize
1. Write a small `Dockerfile` (python slim base, non-root user, `uvicorn` bound to `0.0.0.0:$PORT`).
2. Write `.dockerignore` (venv, `.env`, tests, `.git`).
3. `docker build` and `docker run -e GEMINI_API_KEY=... -p 8080:8080`; hit `/healthz`.

**Done when:** the container answers locally and the image is reasonably small.

### Phase C: GCP foundations (manual first, so you know what the agent automates)
1. Create a **new dedicated project** (e.g. `llm-api-lab`) and link billing.
2. **Create a budget + alert first** (e.g. very low threshold; check current free-tier terms).
3. Install and authenticate the gcloud CLI; set default project and region.
4. Enable APIs: Cloud Run, Cloud Build, Artifact Registry, Secret Manager, Cloud Logging.
5. Create Artifact Registry repo (Docker format) in your region.
6. Create secret `gemini-api-key` and add the key as a version.
7. Create service account `llm-api-sa` with only: `roles/secretmanager.secretAccessor` on that one secret, plus logging write if needed.

**Done when:** `gcloud` shows each resource and you can say why each one exists.

### Phase D: Connect MCP (control plane)
1. Install Node.js 20+ and add the gcloud MCP server (`@google-cloud/gcloud-mcp`) to your MCP client.
2. Confirm it authenticates as *your* gcloud account (its permissions follow that account).
3. Optionally add the Cloud Run MCP (local open-source or Google's remote one; the remote server needs the MCP Tool User role and OAuth/ADC).
4. First read-only prompts: list projects, list enabled APIs, list Cloud Run services.

**Done when:** the agent can list resources in your project, and you have reviewed which commands it can/can't run.

### Phase E: Deploy through the agent
Give the agent narrow, explicit instructions. Examples:
- "Build this folder with Cloud Build and push to Artifact Registry repo X, tag `v1`."
- "Deploy that image to Cloud Run as `llm-api` in region R, service account `llm-api-sa`, mount secret `gemini-api-key` as `GEMINI_API_KEY`, **no unauthenticated access**, max instances 2, memory 512Mi."
- "Show me the service URL and the latest revision status."

Rules for yourself:
- Read every command before approving it. Record prompts and commands in `docs/mcp-session-log.md`.
- Ask the agent to explain each flag you don't recognize.

**Done when:** a revision is serving 100% of traffic and the service is private.

### Phase F: Call it securely (your first real IAM lesson)
1. Grant your own user `roles/run.invoker` on the service (or use the owner account for testing).
2. Call with an identity token: `curl -H "Authorization: Bearer $(gcloud auth print-identity-token)" $URL/healthz`.
3. Try without the token and observe the 401/403.
4. Note in `docs/iam-notes.md` every role and why it exists.

**Done when:** authenticated call works, anonymous call is rejected.

### Phase G: Observe and break things
1. Use the agent (or Logs Explorer) to fetch recent logs for the service.
2. Break it on purpose: wrong secret name, missing role, bad port. Read the error, fix via agent.
3. Deploy a second revision, split traffic 90/10, then roll back.
4. Watch cold start vs warm latency in logs.

**Done when:** you can diagnose each failure from logs alone.

### Phase H: Clean up
1. Delete the service, images, secret versions you no longer need (or the whole project).
2. Confirm in Billing that nothing is accruing.

## 8. IAM touchpoints (where IAM appears naturally)

| When | Identity | Role | Why |
|---|---|---|---|
| Runtime | `llm-api-sa` | `secretmanager.secretAccessor` (on the one secret) | Read the Gemini key |
| Runtime | `llm-api-sa` | `logging.logWriter` | Write logs (often default) |
| Calling the API | Your user | `run.invoker` | Authenticated calls to a private service |
| Using remote Cloud Run MCP | Your user | MCP Tool User | Required by the remote MCP server |
| Deploying | Your user / Cloud Build SA | Build + Artifact Registry writer | Push images |

Principle: the agent should never run with broader access than a person would be comfortable granting.

## 9. Free-tier and safety guardrails

- Dedicated project, budget alert before anything is deployed.
- Cloud Run: `--max-instances 2`, `--min-instances 0`, modest memory/CPU, concurrency left at a sensible value.
- Keep the Gemini call capped (input length, `max_output_tokens`).
- Pick a single region and stay there.
- The agent never gets Owner on a project you care about.
- Free-tier limits change; verify the current Cloud Run, Artifact Registry, Cloud Build and Gemini free quotas before deploying.

## 10. Acceptance criteria

- [ ] `/healthz` and `/v1/chat` work locally and on Cloud Run
- [ ] Key comes only from Secret Manager in prod
- [ ] Service is private; anonymous requests fail
- [ ] Runs as a dedicated service account with least privilege
- [ ] Structured logs visible in Cloud Logging with latency and token counts
- [ ] At least one deliberate failure diagnosed from logs
- [ ] Traffic split and rollback performed once
- [ ] `docs/mcp-session-log.md` and `docs/iam-notes.md` filled in
- [ ] Everything cleaned up or confirmed within free tier
